## Week 13 Day 2: Data Layer

**Completed:** 6 October 2026

**Brief requirement:** "schema.sql executed on RDS PostgreSQL, DynamoDB table created (account_id PK, tx_timestamp sort key), db.py and dynamo.py complete with unit tests passing."

| CI integration job on `develop` with a PostgreSQL service container | `.github/workflows/ci.yml` |

### Key decisions

1. **The sort key is `tx_timestamp`, with the transaction id appended to its value.** Two transactions on one account can share a second; a bare timestamp would let one overwrite the other.
2. **A `by_transaction` index** lets the API fetch one transaction's journey without knowing the account. This is what lets a failed transaction (which never reached the ledger) still be found.
3. **Three database users, one per Lambda.** The ledger is append-only for the score user; the report user is read-only; the query user may change only an alert's resolution columns.
4. **`customers` is a separate table**, so direct personal details are in one place and the score user has no access to them at all.
5. **`risk_level` is stored beside `risk_score`** because the thresholds are configurable, so the level in force at scoring time is a fact, not a derived value.
6. **Seed data is generated by a script with a fixed random seed**, scored with the same rule values the Lambda will use, and includes deliberate patterns for verifying the reports by hand.
7. **Administrator access is through EC2 Instance Connect Endpoint**: no public IP, no inbound rule from the internet, no long-lived key.
