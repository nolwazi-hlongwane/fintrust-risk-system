# API Design

**Brief slot:** Week 13 Day 1: Design Kickoff (specification). Read routes built in Week 13 Day 5; `/alerts` and the write routes in Week 14 Day 1.
**Status:** fourteen routes (read routes in Week 13 Day 5; `/alerts`, `/upload`, `/flag` and `/resolve` in Week 14 Day 1; `/accounts` in Week 14 Day 4; `/insights/trends` and `/accounts/{account_id}/balance`, the data behind the dashboard charts, in Week 15 Day 1; sign-in on every route, the three `/session` routes, sorting and the extra filters in Week 15 Day 2). The machine-readable definition is `infrastructure/apigateway/openapi.json` (OpenAPI 3), which is what API Gateway is built from.

## Overview

| Item | Value |
|---|---|
| Type | Amazon API Gateway **REST API**, regional endpoint, stage `dev` |
| Base URL | `https://{api-id}.execute-api.eu-north-1.amazonaws.com/dev` |
| Backend | One Lambda (`fintrust-capstone-query`) using Lambda proxy integration |
| Transport | HTTPS only |
| Format | JSON, except the body of `POST /upload`, which is CSV text |

## Authentication

Two checks, both made by API Gateway before the Lambda runs, then two more made by the Lambda.

| Check | Answers | Where | Refused with |
|---|---|---|---|
| API key in `x-api-key` | **Which application** is calling, for the usage plan: 10 requests per second (burst 20), 5,000 a day | API Gateway, every route | `403 {"message": "Forbidden"}`, or `429` over the limit |
| Cognito ID token in `Authorization` | **Which person** is calling: signature, issuer and expiry are checked against the user pool | API Gateway's Cognito authorizer, every route except `GET /health` | `401 NOT_SIGNED_IN` |
| Session | Is this sign-in still open? Not signed out, not idle for 15 minutes, under 8 hours old | query Lambda, DynamoDB `fintrust-capstone-sessions` | `401 SESSION_ENDED` with the `reason` |
| Role | Is the person allowed this route? | query Lambda, from the token's Cognito groups | `403 NO_ROLE` or `403 FORBIDDEN` |

There are two API keys on the usage plan: `dashboard-key`, written into the dashboard's `config.js`, and `compliance-key`, used by the verification scripts and the end-to-end test. An API key is not a secret in the way a password is; it identifies an application. On its own it opens only `GET /health`.

The scripts sign in as a dedicated automation user (`fintrust-automation`, compliance-officer role) with Cognito's admin sign-in, which needs the administrator's own IAM credentials. Its password and authenticator secret are generated by `scripts/manage_users.py automation`, kept encrypted in SSM Parameter Store (SecureString) and replaced every time sign-in is deployed; the 6-digit code is worked out by `scripts/totp.py` (RFC 6238). Nothing is printed or written to a file.

### Roles

| Route | `compliance-analyst` | `compliance-officer` |
|---|---|---|
| `GET` routes, `POST /upload` | yes | yes |
| `POST /resolve`, `POST /flag` | no (403 `FORBIDDEN`) | yes |
| `/session` routes | yes | yes |

A signed-in person in neither group gets `403 NO_ROLE` on everything except the `/session` routes. The person who resolves an alert or flags an account is always the signed-in user, taken from the token, never from the request body, so a decision cannot be recorded in someone else's name.

### GET /health

No parameters.

```json
{ "status": "ok", "database": "ok", "version": "0.1.0" }
```

Returns `503` with `"database": "unavailable"` if RDS cannot be reached (for example, the instance is stopped).

### GET /transactions

| Query parameter | Required | Rule |
|---|---|---|
| `account_id` | no | Exact match, e.g. `ACC-1007` |
| `transaction_id` | no | Exact match |
| `risk_level` | no | `LOW`, `MEDIUM` or `HIGH` |
| `tx_type` | no | `CREDIT` or `DEBIT` |
| `channel` | no | `POS`, `ONLINE`, `ATM`, `EFT`, `MOBILE` or `BRANCH` |
| `country_code` | no | Two letters, e.g. `GB` |
| `min_amount`, `max_amount` | no | Rand, inclusive; `min_amount` must not be more than `max_amount` |
| `merchant` | no | Text the merchant name contains, any case, at most 60 characters. `%` and `_` are matched literally |
| `from`, `to` | no | Dates, `YYYY-MM-DD`, inclusive, as South African calendar days |
| `sort` | no | `newest` (default), `oldest`, `amount_desc`, `amount_asc`, `account_asc`, `account_desc`, `merchant_asc`, `merchant_desc`, `score_desc`, `score_asc` |
| `limit` | no | 1 to 100, default 25 |
| `offset` | no | 0 or more, default 0 |

**Sorting** is done by PostgreSQL over the whole result, not by the page, from this fixed list only: the `sort` value chooses one of the API's own `ORDER BY` texts, so nothing the caller sends is ever written into SQL. Every order ends with the newest first and then the id, so rows that tie always come back in the same order and paging never repeats or skips a row. The response says which order was used (`"sort": "amount_desc"`).

```json
{
  "items": [
    {
      "transaction_id": "TXN-20260915-000123",
      "account_id": "ACC-1007",
      "tx_date": "2026-09-15T09:42:11+02:00",
      "amount": "75000.00",
      "currency": "ZAR",
      "tx_type": "DEBIT",
      "channel": "ONLINE",
      "country_code": "GB",
      "risk_score": 70,
      "risk_level": "HIGH"
    }
  ],
  "pagination": { "limit": 25, "offset": 0, "total": 214, "has_more": true }
}
```

Amounts are returned as text so no precision is lost.

### GET /transactions/{transaction_id}/journey

Read from the DynamoDB event store (`"source": "event_store"`). A transaction that was loaded as opening data never passed through the pipeline and has no events; for those the score and the rules that fired are read from the ledger in RDS instead (`"source": "ledger"`, `"events": []`). `404` only if the transaction is in neither.

```json
{
  "transaction_id": "TXN-20260915-000123",
  "account_id": "ACC-1007",
  "source": "event_store",
  "status": "SCORED",
  "score": {
    "risk_score": 70,
    "risk_level": "HIGH",
    "rules": [
      { "rule": "HIGH_AMOUNT", "points": 50, "detail": "75000.00 is above 50000" },
      { "rule": "CROSS_BORDER", "points": 20, "detail": "country GB is not ZA" }
    ]
  },
  "events": [
    { "stage": "RECEIVED", "at": "2026-09-15T07:42:15.120417Z", "detail": "uploads/2026-09-15/batch.csv row 14" },
    { "stage": "VALIDATED", "at": "2026-09-15T07:42:15.120417Z" },
    { "stage": "QUEUED", "at": "2026-09-15T07:42:16.120417Z" },
    { "stage": "SCORED", "at": "2026-09-15T07:42:18.120417Z" },
    { "stage": "ALERT_SENT", "at": "2026-09-15T07:42:20.120417Z" }
  ]
}
```

`status` is one of `RECEIVED`, `QUEUED`, `RETRYING` (scoring has failed once or twice and SQS will try again), `DEAD_LETTERED` (three failures; the message is waiting in the dead-letter queue), `SCORED` or `ALERTED`. A transaction that failed scoring has `"score": null` and one `SCORE_FAILED` event per attempt, each with a plain-language reason.

`404` if the transaction id is unknown.

### GET /insights/trends

*Week 15 Day 1.* The four series the dashboard draws as charts. Optional `from` and `to` dates, as for `/insights`. PostgreSQL does all the counting; the browser only draws the result, so every chart can be checked against SQL.

| Part | What it is | How it is worked out |
|---|---|---|
| `granularity` | How wide each bar is: `day` (periods up to 62 days), `week` (up to two years, weeks start on Monday) or `month` | Chosen by the API from the length of the period |
| `activity` | Transactions per bar, split Low, Medium and High, with their value. Empty bars are included so the time axis has no gaps | `date_trunc` on the South African calendar day |
| `score_distribution` | How many transactions fall in each score range 0-9 ... 90-100, split by the level they were given, with the thresholds | Integer division of `risk_score` |
| `alert_flow` | Alerts raised and resolved per bar, the number open now, and the median hours from raised to resolved | `percentile_cont(0.5)` |
| `account_ranking` | The top 15 accounts by total risk points: `fraud_rank`, `fraud_percentile` and whether the account broke the 30-day burst rule | The same `PERCENT_RANK()` and rolling `RANGE BETWEEN INTERVAL '30 days'` window as `sql/risk_report.sql`, over all accounts before the top 15 are kept |

```json
{
  "period": { "from": null, "to": null },
  "span": { "first_day": "2026-07-01", "last_day": "2026-09-30" },
  "granularity": "week",
  "activity": [
    { "period_start": "2026-06-29", "low": 17, "medium": 2, "high": 1, "transactions": 20, "total_value": "621909.15" }
  ],
  "score_distribution": {
    "bucket_size": 10,
    "thresholds": { "medium": 40, "high": 70 },
    "buckets": [ { "from": 0, "to": 9, "low": 235, "medium": 0, "high": 0 } ]
  },
  "alert_flow": {
    "periods": [ { "period_start": "2026-06-29", "raised": 1, "resolved": 1 } ],
    "raised": 12, "resolved": 9, "open_now": 3, "median_hours_to_resolve": "26.0"
  },
  "account_ranking": {
    "accounts_ranked": 12,
    "burst_rule": "more than 3 high-risk transactions in any 30 days",
    "items": [
      { "account_id": "ACC-1005", "account_status": "ACTIVE", "transaction_count": 30, "high_risk_count": 4,
        "total_risk_points": 580, "fraud_rank": 1, "fraud_percentile": "1.0000",
        "peak_high_risk_in_30_days": 2, "burst_detected": false },
      { "account_id": "ACC-1007", "account_status": "FLAGGED", "transaction_count": 31, "high_risk_count": 5,
        "total_risk_points": 550, "fraud_rank": 2, "fraud_percentile": "0.9091",
        "peak_high_risk_in_30_days": 5, "burst_detected": true }
    ]
  }
}
```

(Arrays shortened.) An integration test checks that every account in `sql/risk_report.sql`'s output has the same rank, percentile and 30-day peak here, and that the activity series adds up to `/insights` exactly.

### GET /accounts/{account_id}/balance

*Week 15 Day 1.* One account's running balance, one point per transaction, oldest first. Optional `from` and `to` dates.

The balance comes from the project's own `sql/monthly_summary.sql` (`SUM(...) OVER (PARTITION BY account_id ORDER BY tx_date, transaction_id ROWS UNBOUNDED PRECEDING)`), packaged with the Lambda, so the chart, the monthly report and the SQL artefact use one query. The account and date filters are applied **outside** the window function: each balance is worked out from the account's whole history first, so a chosen period starts from the true balance instead of zero. PostgreSQL still reads only that account's rows (the account filter matches the window's `PARTITION BY`, so it is applied before the window, through the `account_id` index).

At most the latest 1,000 points are returned; `truncated` says when there were more.

```json
{
  "account_id": "ACC-1007",
  "account_status": "FLAGGED",
  "period": { "from": "2026-09-01", "to": "2026-09-30" },
  "points": [
    { "transaction_id": "TXN-20260902-000180", "tx_date": "2026-09-02 13:29:00+00:00", "tx_type": "DEBIT",
      "amount": "81900.00", "signed_amount": "-81900.00", "running_balance": "423779.20",
      "risk_level": "HIGH", "risk_score": 70 }
  ],
  "truncated": false,
  "summary": {
    "opening_balance": "505679.20", "closing_balance": "388419.28",
    "lowest_balance": "388419.28", "highest_balance": "610279.20",
    "credits": "186500.00", "debits": "303759.92", "high_risk_transactions": 3
  }
}
```

`opening_balance` is the balance carried in from before the period: opening + credits − debits = closing. An unknown account is `404`; a malformed id is `400`.

### POST /upload

Accepts the file and returns immediately. Processing continues in the background: the file is stored in the raw bucket, and S3 invokes the ingest Lambda asynchronously.

| Part | Rule |
|---|---|
| Header | `Content-Type: text/csv` |
| Query | `filename` (optional; letters, digits, `-`, `_`, `.` only) |
| Body | CSV text with a header row, at most 5 MB |

```json
{
  "status": "ACCEPTED",
  "upload_id": "0f4c2d8e-6f1b-4b1c-9d0f-5f6d0f1a2b3c",
  "object_key": "uploads/2026-10-06/0f4c2d8e-batch.csv",
  "message": "File accepted. Transactions will appear as they are processed."
}
```

Status `202 Accepted`. `400` for an empty body, a header row with missing columns, a file that is not UTF-8 text or an unsafe `filename`; `413` if larger than 5 MB; `503` if the file could not be stored.

The object key is always built by the API (`uploads/<date>/<8 characters of the upload id>-<filename>`); it is never taken from the caller. Only the header is checked here. Each row is validated by the ingest Lambda, and the progress of any transaction can be followed with `GET /transactions/{transaction_id}/journey`.

### POST /flag

```json
{ "account_id": "ACC-1007", "reason": "Four high-risk transactions in 30 days" }
```

Compliance officers only. Calls the `flag_account` database function, which inserts a `risk_events` row (with `flagged_by`, the signed-in officer's username) and sets the account status to `FLAGGED` in one atomic step.

```json
{ "risk_event_id": 381, "account_id": "ACC-1007", "account_status": "FLAGGED", "flagged_by": "n.hlongwane" }
```

Status `201`. `400` if a field is missing or `reason` is longer than 500 characters, `403` for an analyst, `404` if the account does not exist, `409` if the account is closed.

### POST /resolve

Compliance officers only.

```json
{ "alert_id": 57, "resolution_note": "Confirmed with customer" }
```

```json
{ "alert_id": 57, "status": "RESOLVED", "resolved_at": "2026-10-07 11:05:00.482113+00:00", "resolved_by": "n.hlongwane" }
```

Status `200`. `400` if `alert_id` is not a positive whole number; `403` for an analyst; `404` if the alert does not exist; `409` if it is already resolved. `resolution_note` is optional (at most 500 characters). `resolved_by` is the signed-in officer's username; a `resolved_by` in the body (sent by clients before Week 15 Day 2) is ignored.

### The session routes

`POST /session` is called once, straight after sign-in. It records one item in `fintrust-capstone-sessions`, keyed by the token's `origin_jti` (Cognito keeps it the same when a token is refreshed, so one sign-in is one session). Calling it again for the same sign-in returns the same session with `200`; a session that has ended can never be started again.

```json
{
  "username": "n.hlongwane", "name": "Nolwazi Hlongwane", "roles": ["compliance-officer"], "status": "ACTIVE",
  "started_at": "2026-10-13T08:02:11Z", "last_seen_at": "2026-10-13T08:02:11Z", "ends_at": "2026-10-13T16:02:11Z",
  "idle_minutes": 15,
  "permissions": { "read": true, "upload": true, "resolve_alerts": true, "flag_accounts": true }
}
```

`GET /session` returns the same shape. `DELETE /session` returns `{"status": "ENDED", "end_reason": "SIGNED_OUT"}`.

## Errors

Every error produced by the Lambda has the same shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "limit must be between 1 and 100",
    "request_id": "c6af9ac6-7b61-11e6-9a41-93e8deadbeef"
  }
}
```

| Status | Code | When |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Bad parameter or body |
| 401 | `NOT_SIGNED_IN` | No ID token, or one that is not valid (answered by API Gateway) |
| 401 | `SESSION_ENDED` | The sign-in has ended; `reason` is `SIGNED_OUT`, `IDLE`, `EXPIRED`, `REVOKED` or `NOT_STARTED` |
| 403 | `NO_ROLE` | Signed in, but in neither compliance group |
| 403 | `FORBIDDEN` | An analyst tried to resolve an alert or flag an account |
| 404 | `NOT_FOUND` | Unknown route, transaction, account or alert |
| 409 | `CONFLICT` | Alert already resolved |
| 413 | `PAYLOAD_TOO_LARGE` | Upload above 5 MB |
| 500 | `INTERNAL_ERROR` | Unexpected failure. The database transaction is rolled back, the detail is logged with the `request_id`, and no internal detail is returned to the caller |
| 503 | `SERVICE_UNAVAILABLE` | Database, event store or session store unreachable. The API fails closed: a session that cannot be checked is not let through |

## Cross-origin access (CORS)

The API allows browser calls only from the dashboard's CloudFront address, with headers `authorization`, `content-type` and `x-api-key` and methods `GET`, `POST` and `DELETE`.

How it works:

1. The setting `cors_allowed_origin` in SSM holds the dashboard's address. `deploy_frontend.sh` writes it.
2. A browser sends the page's address in the `Origin` header. If it is on the list, the Lambda returns it in `Access-Control-Allow-Origin`, and the browser lets the page read the response.
3. For any other origin the Lambda returns the dashboard's address, which does not match the caller's, so that browser refuses to hand over the response.
4. Errors produced by API Gateway itself (a missing key, a missing or expired token, a throttled request) never reach the Lambda, so the same address is set on the gateway's default 4xx and 5xx responses and on its 401 response when the API is deployed. Without that, the dashboard could not tell "your sign-in has expired" from a network failure.
5. `OPTIONS` preflight requests need no API key (a browser cannot attach one) and return only the CORS headers.

Every response also carries `Vary: Origin`, so a cache cannot reuse one site's answer for another.

CORS protects users' browsers from other websites. It is not authentication: `curl` ignores it, which is why every route still requires the API key and, except `GET /health`, a signed-in person.
